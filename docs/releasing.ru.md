# Выпуск версии

`BimZen.Bcf.Core` публикуется на nuget.org рабочим процессом
[`.github/workflows/release.yml`](../.github/workflows/release.yml), который
запускается тегом версии.

Ключа API в этом репозитории нет, и заводить его не нужно. nuget.org меняет
токен OIDC от GitHub на временный ключ со сроком жизни в час — ничего
долгоживущего нигде не хранится. Сам nuget.org теперь
[не рекомендует ключи API](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing)
для автоматической публикации.

## Разовая настройка

Делается один раз владельцем пакета.

1. **Политика доверенной публикации** — на nuget.org под своим именем →
   **Trusted Publishing** → добавить политику:

   | Поле | Значение |
   | --- | --- |
   | Repository Owner | `kichnap` |
   | Repository | `bimzen-bcf` |
   | Workflow File | `release.yml` |
   | Environment | оставить пустым |

   Файл рабочего процесса указывается **только именем**, без
   `.github/workflows/`. Переименование файла ломает публикацию, пока политику
   не поправят, — в этом и смысл.

   Для публичного репозитория политика действует сразу. Для приватного она
   семь дней держится во временном состоянии: nuget.org нужны идентификаторы
   репозитория и владельца, которые приходят с первой успешной публикацией, —
   ими политика привязывается к репозиторию на случай, если его удалят
   и создадут заново под тем же именем. Семидневное окно можно перезапустить
   в любой момент.

2. **Переменная `NUGET_USER`** — в этом репозитории, в разделе
   Settings → Secrets and variables → Actions → Variables. Её значение —
   **имя профиля** на nuget.org, а не адрес почты. Именно переменная,
   а не секрет, и намеренно: это не учётные данные, а отсутствующий секрет
   роняет шаг входа, не объясняя причины.

   Если политикой владеет организация, а не человек, значением всё равно
   остаётся имя профиля учётной записи, от которой идёт публикация.

## Как выпустить версию

1. Заполнить `CHANGELOG.md` и `CHANGELOG.ru.md` — перенести `[Unreleased]`
   под новый номер.
2. Проставить `<Version>` в `Bcf.Core/Bcf.Core.csproj`.
3. Закоммитить, поставить тег и запушить:

   ```bash
   git tag v1.1.0 && git push origin main --tags
   ```

Рабочий процесс отказывается публиковать, если тег и `<Version>` расходятся,
затем прогоняет тесты, собирает пакет, просит у nuget.org временный ключ
и публикует. Пакет символов (`.snupkg`) уходит вместе с ним; `.nupkg` заодно
сохраняется артефактом сборки, чтобы при неудачной публикации его можно было
посмотреть, ничего не пересобирая.

`--skip-duplicate` стоит намеренно: повторный запуск на уже опубликованной
версии должен ничего не делать, а не давать красную сборку.

## Если что-то пошло не так

**Шаг входа падает без объяснений.** Чаще всего в задании потерялось
`id-token: write` — без него GitHub вообще не выдаёт токен. В рабочем процессе
оно есть; проверьте, что его не убрала правка.

**nuget.org отвергает токен.** Политика перестала совпадать: файл рабочего
процесса переименован, репозиторий переехал или политика заведена на другого
владельца. Политики отключаются и тогда, когда создавший её человек вышел
из организации-владельца, и включаются обратно, когда его возвращают.

**Версия уже опубликована.** Версии на nuget.org нельзя заменить, можно
только скрыть из списка. Выпускайте следующий номер.
