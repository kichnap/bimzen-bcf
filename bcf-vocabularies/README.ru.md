# Справочники BCF — единый источник правды

Эта папка задаёт согласованные значения `TopicType`, `TopicStatus`,
`Priority`, `TopicLabel`, `Stage` и отображение статусов, приходящих
из инструмента поиска коллизий.

**Правится только `bcf-extensions.json`.** Всё остальное — производное.

## Состав

| Файл | Назначение |
|---|---|
| `bcf-extensions.json` | Канонический справочник: wire-значения, подписи, семантика, цвета, разрешённые переходы, таблицы отображения |
| `extensions.xml` | Готовый файл для корня `.bcfzip` (BCF 3.0) |
| `README.md` | Правила, обоснования, заметки по интеграции |

## Ключевое решение: wire-значения английские

В BCF **нет пары «идентификатор + отображаемое имя»**. Поле `TopicStatus`
в `markup.bcf` — обычная строка, и сторонние приложения (Solibri,
BIMcollab Zoom, Revizto) показывают её пользователю буквально.

Отсюда:

- Машинные значения — английские ASCII: `In Progress`, `Clash`, `Critical`.
- Локализованные подписи применяются **только в интерфейсе**, через таблицу
  `labels`.
- Не-ASCII текст никогда не попадает в файл и в тело HTTP.

Обратный выбор — локализованные значения на проводе — выглядит удобнее
в первый день и ломается на второй: чужие парсеры спотыкаются
на кодировках, а данные перестают быть переносимыми.

## Правила изменения справочника

1. **Wire-значения неизменяемы после первого выпуска.** Переименование
   статуса — это миграция всех замечаний на сервере и расхождение с уже
   отправленными архивами.
2. **Добавлять можно, удалять — нет.** Вышедшее из употребления значение
   помечается `deprecated: true`, скрывается при создании и продолжает
   корректно отображаться в старых данных.
3. **Версия справочника** (`vocabularyVersion`) — semver. Мажорная при
   несовместимых изменениях, минорная при добавлении значений. Сервис должен
   отдавать её клиентам, чтобы клиент мог предупредить о расхождении.
4. Сравнение **строгое, с учётом регистра и пробелов**: `In Progress` ≠
   `in progress` ≠ `InProgress`.

## Модель жизненного цикла

```
New ──► Assigned ──► In Progress ──► Resolved ──► Closed
 │          │             │              │           │
 │          │             │              └─► Reopened┘
 │          │             │                     │
 └──────────┴─────────────┴─► Deferred ◄────────┘
 └──────────┴─────────────────► Rejected
```

Решения, которые стоит понимать:

- **`Resolved` не конечный.** Исполнитель заявляет об устранении,
  координатор подтверждает после следующей выгрузки модели. Смешать
  «исполнитель сказал» и «проверено» в один статус — самая частая ошибка
  в подобных системах: метрики перестают отражать реальность.
- **`Reopened` — отдельный статус, а не возврат в `Assigned`.** Он нужен
  ради метрики повторных возвратов: доля переоткрытых замечаний говорит
  о качестве работы дисциплины больше, чем общее число коллизий.
- **`Rejected` и `Deferred` требуют комментария** (`requiresComment: true`).
  Закрытие без обоснования — то, чем система обесценивается через месяц
  эксплуатации.
- **`Assigned` и `In Progress` требуют исполнителя**
  (`requiresAssignee: true`).

`allowedTransitions` предназначено для проверки на сервере. Клиент может
использовать его, чтобы не предлагать невозможных переходов, но
**авторитетная проверка — на сервере**: клиенту доверять нельзя, а сторонние
клиенты о ваших переходах не знают вовсе.

## Неоднозначность, которую каждое внедрение решает само

Статус `Approved` инструмента поиска коллизий используют двояко:

| Трактовка | Целевой статус BCF | Когда выбирать |
|---|---|---|
| «Исправление проверено и принято» | `Closed` (текущее умолчание) | Координатор ведёт весь цикл в инструменте коллизий |
| «Пересечение признано допустимым» | `Rejected` | `Approved` используется как согласованное отступление |

Отображение переопределяется в настройках выгрузки; умолчание стоит
выставить под фактическую практику ваших координаторов. Сейчас
в `bcf-extensions.json` стоит `Closed`.

## Асимметрия обратного отображения

Набор статусов инструмента коллизий (`New`, `Active`, `Reviewed`,
`Approved`, `Resolved`) беднее приведённого выше. Поэтому подтягивание
статусов обратно с сервиса координации теряет информацию: `Assigned`,
`In Progress` и `Reopened` сворачиваются в `Active`.

Следствие: **инструмент поиска коллизий не может быть источником правды
по статусам.** Полный статус живёт на сервере; то, что записывается обратно
в результат проверки, — удобство для тех, кто смотрит только в родной
интерфейс. Логику на этом строить нельзя.

## Асимметрия проверки: строго на выход, терпимо на вход

Стандарт не фиксирует справочники — их объявляет каждая реализация. Значит,
**входящие файлы от чужих инструментов будут содержать значения, которых
в этом справочнике нет**: BCF из Revizto, BIMcollab или Solibri придёт
со своими статусами и типами, и это полностью законно.

Отсюда два разных режима:

| Направление | Поведение |
|---|---|
| **Исходящее** (создание замечаний, POST в API, запись файла) | Строгая проверка. Значение вне справочника — ошибка, `422` с перечислением допустимых |
| **Входящее** (импорт `.bcfzip`, приём замечаний от чужих клиентов) | Значение сохраняется **как есть**, замечание не отвергается. В интерфейсе показывается с пометкой «внешнее», нейтральным цветом, и не участвует в проверке переходов |

На сервере:

- Храните `topic_status` строкой, а не ссылкой на enum-таблицу. Внешний
  ключ на справочник поймает вас на первом же импорте извне.
- Держите отдельный вычисляемый флаг вроде `is_known_status` — по нему
  строятся метрики и фильтры, чтобы внешние значения не искажали статистику.
- Дайте координатору механизм **ручного сопоставления**: «`Открыто`
  из чужого файла → наш `New`», с сохранением исходного значения в истории
  замечания.
- То же для `topic_type`, `priority`, `labels` и `stage`.

Отвергнуть импорт из-за незнакомого статуса — самый быстрый способ получить
репутацию инструмента, который «не понимает openBIM».

## Интеграция: сервис (Node/TypeScript)

1. Держите `bcf-extensions.json` в репозитории как единственный источник
   справочников. Не заводите параллельные enum'ы в коде.
2. Генерируйте типы и константы на этапе сборки:

```ts
import vocab from './bcf-extensions.json';

export const TOPIC_STATUSES = vocab.topicStatuses.map(s => s.value);
export type TopicStatus = (typeof vocab.topicStatuses)[number]['value'];

export const TRANSITIONS = Object.fromEntries(
  vocab.topicStatuses.map(s => [s.value, s.allowedTransitions])
);
```

3. Отдавайте `GET /bcf/3.0/projects/{id}/extensions` **из этого же файла**,
   а не из захардкоженного ответа. Иначе расхождение между файловым каналом
   и API гарантировано.
4. Проверяйте `topic_status`, `topic_type`, `priority`, `labels` и `stage`
   **при создании и изменении через ваши собственные клиенты** — вне
   справочника отвечайте `422` с перечислением допустимых. При **импорте
   файлов и приёме от сторонних клиентов** проверку не применяйте:
   сохраняйте значение как есть (см. раздел об асимметрии проверки).
5. Проверяйте переходы по `allowedTransitions` и отклоняйте невозможные
   с `409`.
6. Проверяйте `requiresComment` и `requiresAssignee` перед сменой статуса.

## Интеграция: хост на .NET

1. `bcf-extensions.json` уже встроен ресурсом в `Bcf.Core`.
2. Константы генерируются из него — **не пишите строки руками по месту
   вызова**. См. `Bcf.Vocabulary.Generator`.
3. Разумные умолчания выгрузки: `TopicType = Clash`, `Priority = Normal`,
   `Stage = Design`, статус — через `navisworksStatusMapping`.
4. Метку дисциплины (`ARC`, `HVAC`, …) выводите из имени проверки
   на коллизии или из выбранных наборов, с возможностью ручного
   переопределения.
5. Метку `Auto` ставьте на всё, что выгружено автоматически: она позволяет
   принимающему сервису отличать автоматические коллизии от заведённых
   вручную замечаний без разбора текста.
